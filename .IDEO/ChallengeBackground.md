# Challenge

**为长期使用 Claude Code 的人，设计让 agent 免于腐烂的记忆系统：记忆与用户、项目持续保持同步；每一次自动整合都增强而非侵蚀信任——可溯源、可撤销。**

> 势力范围：整合可维护记忆文件与 CLAUDE.md，绝不触碰其他项目内容。
>
> 非目标（本轮收窄）：团队共享记忆（team/、多人协作）；跨项目记忆（未来方向）。

## Background

### 为什么是现在

项目在 2026-07-29 重启——此前的 Design Sprint 与 Scrum Sprint 1-6 产出因组织杂乱作废，完整历史仍留在 git 里，但不再是当前工作基础。重启要重新框定一个值得数月投入的方向，本身是个高风险决定（high stakes）。摆在眼前的时间窗口来自一个具体观察：Claude Code 官方的离线记忆整合功能（内部称 "Auto Dream"）在这台机器上从未真正跑起来过——服务端 gate（`tengu_onyx_plover`）一直未放行（推测：可能与本机走的第三方网络中转有关，这一判断的代表性存疑）。

### 官方现状：不是"还没做"，是"做了但没写文档、没做透明层"

Ask the Experts 阶段（2026-08-01）证实，Auto Dream 并非一个尚在酝酿的未来功能，而是一个已经在其他用户机器上真实运行、却始终没有出现在官方文档（`code.claude.com/docs/en/memory`）里的研究预览功能——触发条件是 24 小时冷却期加 5 次新会话，且需服务端 gate 放行。社区已经暴露出真实事故：一名用户报告 Auto Dream 在 24 小时内静默删除了 23 个记忆文件（其中包括他反复强调过的规则），没有任何确认或变更日志，只能靠自建备份对比才发现（issue #47959）；另一份社区分析把官方实现的缺口归纳为三类——身份（项目改名后记忆变孤儿）、准确性（整合时写下的具体数字不核实原文）、透明度（唯一线索是"上次运行于 X 秒前"）（issue #38493）。这三个缺口与 Challenge 里"可溯源、可否决、可撤销"的要求几乎一一对应——不是我们凭空设想的风险，是已经被实测证实的官方产品缺陷。两个 issue 都被机器人以 stale 自动关闭，未见产品团队正面回应：这块地没人种，但也没人明确说不让种。

### 原料层是否可行

会话日志（jsonl）在本机真实可得——`~/.claude/projects/` 下约 30 个项目、单项目常有 40+ 份会话文件。但官方 Auto Dream 依赖的 `logs/` 逐日活动流压缩层，本机全部项目均不存在——这不是本项目的个例，是这台机器上整层都还是暗的，意味着这层必须自建，是这个方向里最大的一块工程量。SessionEnd、PreCompact、SessionStart 都是可挂钩的钩子，但 SessionEnd 触发之后没有 LLM 在运行——插件形态目前没有一个"免费"的离线时刻可以白嫖。

### 差异化在哪

不在整合算法本身：claude-memory-compiler、官方 Auto Dream、AI 转化产物 claude-dream 三条路径的四阶段流程彼此同构，抄哪条都构不成差异化。真正的空间在信任与所有权层——① **变更凭证 + git 可回滚**：这正是官方三个缺口的解药，而官方不敢让 Auto Dream 改 CLAUDE.md，本质上是因为它没有回滚层，我们有 git，敢做官方不敢做的事；② **记忆容器身份的稳定性**：官方记忆按工作目录路径字符串键控，项目改名或搬盘会静默孤立记忆——本项目自己在 2026-07-29 重启搬盘时就实际踩过这个坑，官方似乎还没意识到这个问题；③ **本地可控、可否决**：第三方工具 claude-mem 在官方方案已经上线的情况下依然有约 4.6 万 star，证明"更可控、更本地"的需求是真实存在的，不是我们臆想出来的窗口。
