# Challenge

**为长期使用 Claude Code 的人，设计让 agent 免于腐烂的记忆系统：记忆与用户、项目持续保持同步；每一次自动整合都增强而非侵蚀信任——可溯源、可撤销。**

> 势力范围：整合可维护记忆文件与 CLAUDE.md，绝不触碰其他项目内容。
>
> 非目标（本轮收窄）：团队共享记忆（team/、多人协作）；跨项目记忆（未来方向）。
>
> 为何值得冲刺：项目重启（stuck）+ 框定决定数月投入（high stakes）；官方 auto-dream 本机从未放行（推测：可能受本机第三方网络中转影响，代表性存疑），但社区证据显示它已在其他用户处真实运行且暴露出事故——窗口期不是"还没开始"，是"已经开始但没写文档、没做透明层"。
>
> 整合原料层可行性（Ask the Experts 已验证，2026-08-01）：会话 jsonl 真实可得（本机 `~/.claude/projects/` 下约 30 个项目、单项目 40+ 份会话文件）；但官方 auto-dream 依赖的 `logs/` 逐日活动流压缩层，本机全部项目均不存在——不是本项目个例，是这台机器上整层都是暗的，须自建，这是核心工程量。SessionEnd / PreCompact / SessionStart 均可挂钩，但 SessionEnd 之后没有 LLM 在跑，插件形态目前没有免费的"离线时刻"。
>
> 差异化定位（Ask the Experts 已验证，2026-08-01）：不在整合算法本身——claude-memory-compiler、官方 auto-dream、AI 转化产物 claude-dream 三条路径的四阶段流程彼此同构，抄哪条都不构成差异化。差异化在信任与所有权层：① **变更凭证 + git 可回滚**——官方已实测的三个缺口（身份、准确性、透明度）的直接解药，且官方不敢让 dream 改 CLAUDE.md 正是因为它没有回滚层，我们有 git 敢做；② **记忆容器身份稳定性**——官方记忆按工作目录路径字符串键控，项目改名/搬盘会静默孤立记忆（本项目自己在 2026-07-29 重启搬盘时已实际踩过这个坑），官方未意识到此问题；③ **本地可控、可否决**——第三方 claude-mem 在官方方案已上线的情况下仍有约 4.6 万 star，证明"更可控、更本地"的需求真实存在，不是臆想的窗口。
